# 警報訂閱：網站選擇、LINE 接收

狀態：討論紀錄（2026-10-22），尚未開發。這份文件記錄使用者與 Claude 的討論結果，功能程式碼沒有修改。相關文件：[VISION.md](VISION.md)（第三支柱「警報與訊號訂閱」）、[ORDERFLOW-KEYLEVEL-ALERTS.md](ORDERFLOW-KEYLEVEL-ALERTS.md)（關鍵位警報、影子模式、回測）、[ORDERFLOW-PLATFORM.md](ORDERFLOW-PLATFORM.md)（收集器）。

## 使用者的想法

覆盤影片已經做好。導流不直接導到 LINE，改成導到網站：用戶在網站上選擇要訂閱哪些指標，按下「透過 LINE 接收通知」後，連到 MetaBear 官方 LINE 並自動帶入關鍵字，送出即訂閱成功。直接導到 LINE 也可以，但網站的介面可以做得比 LINE 完整、好看。

## 已決定（2026-10-22）

- **網站選擇，LINE 接收**：訂閱的介面放在網站，LINE 只負責確認訂閱和推播。
- **兩個入口並存**：
  - **獨立訂閱頁**（暫稱 `/alerts`）：覆盤影片的落地頁，完整介紹每一種警報。
  - **實驗室 `/lab/orderflow/` 裡的訂閱面板**：用戶邊看圖邊訂閱。
  - 兩邊共用同一套元件與同一份警報清單。
- **兩種通知管道，門檻不同**（使用者原話：「普通用戶開著我們的網頁都能直接收到通知，每個項目都可以收到。要開通 LINE 通知必須綁定邀請碼。」）：

  | 管道 | 誰可以用 | 範圍 | 成本 |
  | --- | --- | --- | --- |
  | **網頁通知** | 所有人，不用登入 | 每一種警報都能選，**只通知關鍵位上的事件** | 不花 LINE 額度 |
  | **LINE 通知** | 綁定 BingX 邀請碼**並且入金 200 USDT** 的用戶（見下面的「LINE 通知的資格」一節） | 用戶自選的警報，**只推關鍵位上的事件** | 每則推播都用掉 LINE 額度 |

  網頁通知是免費的體驗，LINE 通知是綁定邀請碼的獎勵：「想關掉網頁也收得到？綁定邀請碼開通 LINE 通知。」這也是 VISION 路線圖第 4 階段「透過 BingX 邀請碼解鎖進階警報」的第一步。
- **「在關鍵位」的門檻統一成 0.1%**（2026-10-22）：事件價格離最近的關鍵位在 0.1% 以內（BTC 約 $100）才算。收集器（`watch.js` 的 `levelTolPct`）本來就是 0.1%；實驗室圖表的 `signals.js`（`P.levelTolPct = 0.0015`，也就是 0.15%）要改成 0.1%。
- **LINE 先用免費方案**（2026-10-22）：每月 200 則，真的不夠用再升級。
- **LINE 通知的使用者選項**（2026-10-22）：除了事件類型，用戶也能選**每天最多幾則**和**安靜時段**（例如 00:00～08:00 不推）。每天則數的上限由管理頁的 `dailyCap` 決定，用戶只能選上限以內的數字。安靜時段內的事件直接放棄，不會等到早上補推（過時的事件沒有價值）。
- **關鍵位換日改成 UTC 日**（台灣早上 8 點），由 Claude 決定，理由見下面的「關鍵位換日」一節。這推翻 2026-10-20 的「換日用台灣時間」。
- 本文件之後要開發，仍以 [VISION.md](VISION.md) 的原則為準：**事件不是指令**、不公布命中率、所有頁面與訊息附「非投資建議」。

## 整體架構：同一個引擎、三個出口

```
            Bybit 收集器（偵測事件：吸收、掃蕩、冰山、誘單…）
               │                 │                  │
               ▼                 ▼                  ▼
     實驗室圖表上的事件記號    LINE 推播給訂閱者     訂閱頁上的案例卡片
```

訂閱頁是這個引擎的「設定頁」：決定哪些事件要推到用戶的 LINE。

### 三條連結（建議做法）

1. **警報 → 實驗室**：每則 LINE 警報都附上實驗室連結，打開事件發生的那一分鐘。現在已經有雛形（`src/orderflow/collector.ts` 送出 `/lab/orderflow/?tf=1&at=…`）。要補的是：把該事件標亮，並自動切到看懂它需要的畫面（例如吸收 → 足跡圖加 Delta）。這對應「警報是提醒，判斷看後續訂單流」的定位。
2. **實驗室 → 訂閱**：點圖表上的事件記號會跳出小卡片：事件名稱、發生在哪個關鍵位、對應課程，以及「在 LINE 收到這類提醒」按鈕。
3. **訂閱頁 → 實驗室**：每種警報卡片附「看最近一次發生」，連到實驗室的那一刻。卡片上的範例都是真實、可回溯的盤面（VISION 原則 2），不是示意圖。

### 導流路線

```
覆盤影片 → 訂閱頁（每種警報的說明，範例連到實驗室）→「透過 LINE 接收通知」
        → LINE 確認訂閱 → 之後每則警報都把人帶回實驗室
```

實驗室是用戶每天回來的地方，LINE 是叫他回來的鈴聲。

## 前提：圖表與警報必須是同一套事件

目前兩者不一致，串起來之前要先處理：

| 項目 | 實驗室圖表 | LINE 警報 |
| --- | --- | --- |
| 事件來源 | 瀏覽器用 `signals.js` 在 5 分 K 上計算（`app.js` 的 `detect()`） | 收集器用 `watch.js`（爆倉、OI、掛單牆、冰山、誘單），加上關鍵位閘門 |
| 關鍵位換日 | UTC 日 | 台灣日（Asia/Taipei 午夜） |

用戶點警報連結進來，如果圖上看不到同一個事件，或關鍵位畫在別的價位，就會覺得對不上。做法：

- 圖表、網頁通知和 LINE 通知都使用**收集器實際發出的事件**（同一份 `alerts` 紀錄），不另外在瀏覽器算一套。
- 收集器和 `keylevels.js` 的關鍵位與 VWAP 改成 UTC 日，和網頁目前的畫法一致（見下一節）。

## 關鍵位換日：UTC 日（2026-10-22 決定）

前日高低、POC、VAH、VAL 和 VWAP 都以 **UTC 00:00（台灣早上 8 點）**換日。理由：

1. **和用戶在別處看到的一致**。Bybit、幣安和 TradingView 上的加密貨幣日 K 都是 UTC 收盤。用戶拿我們的「前日高點」去和自己圖上的日 K 對照，數字要一樣，不然會懷疑是我們算錯。
2. **前日關鍵位可以早一點用封存檔定案**。Bybit 每日成交封存檔是按 UTC 日切的，前一天的檔案約在 01:10 UTC 匯入，也就是換日後約 1 小時就能用完整資料重算。改成台灣日的話，前一個台灣日橫跨兩個封存檔，後半段要等到換日後約 9 小時才有檔案，這段時間只能用可能有缺口的即時資料。
3. **改動最小**。網頁的前日關鍵位和 VWAP 本來就是 UTC 日，只要改收集器的影子模式和 `keylevels.js`（目前用 Asia/Taipei 午夜），不用動網頁。

注意事項：

- 訊息和課程要寫清楚「前日」是指「台灣早上 8 點換日」，例如「前日高點（日 K，早上 8 點換日）」。
- 第 5b 節的 90 天回測用的是台灣日。警報本來就定位成提醒，不用回測結果挑事件，所以不用為了換日重跑；但之後若引用那份回測，要記得換日不同。
- 每日推播上限 `dailyCap` 是在控制 LINE 額度，不是盤面邏輯，可以繼續用台灣日計算。

## 網頁通知的技術做法

- **事件來源**：實驗室目前的即時資料是瀏覽器直接連 Bybit WebSocket；收集器的 `/api/orderflow/btcusdt/alerts` 需要管理員 token，而且帶有調整門檻的功能。要新增一個**公開、唯讀**的事件端點（例如 `GET /api/orderflow/btcusdt/events?since=`），只回傳事件，不含設定與內部欄位。網頁每 10～15 秒拉一次，端點用邊緣快取幾秒鐘，避免很多人同時開著網頁時打爆收集器。
  - 不建議讓瀏覽器自己用 `watch.js` 算事件：觀察器需要累積狀態（例如持續 60 秒的條件），網頁剛打開時會和收集器不一致，又回到「圖表和警報對不上」的問題。
- **通知方式**：用瀏覽器的 Notification API；用戶在訂閱頁或實驗室面板勾選事件類型，再按「允許通知」。設定存在瀏覽器本機（`localStorage`），不用登入。分頁在背景時也收得到，但網頁必須開著。
- **收不到系統通知的情況，要退回頁面內提示**（畫面角落的提示框加提示音）：
  - **LINE 內建瀏覽器**不支援 Notification API。從 LINE 點連結進來的用戶很多，頁面要提示「用 Safari／Chrome 開啟」或「綁定邀請碼開通 LINE 通知」。
  - **iPhone Safari** 只有在「加入主畫面」之後才支援網頁通知（iOS 16.4 以上）。
- 網頁通知不花 LINE 額度，不需要每日上限；但同一類事件短時間內要合併，免得一直跳。
- 「網頁關掉也想收到」需要 Web Push（Service Worker 加推播伺服器），這次不做。用戶說的是「開著網頁」；網頁關掉以後的通知交給 LINE 通知。

## LINE 端的技術做法

- 按鈕連到 `https://line.me/R/oaMessage/@<官方帳號 ID>/?<URL 編碼的關鍵字>`。LINE 會打開官方帳號的聊天室，並把文字預先填好。
- **LINE 不允許自動送出**，用戶要自己按「傳送」。流程是「點按鈕 → 跳到 LINE → 按傳送 → 收到確認」。
- 確認訊息是回覆（reply），不計入每月推播額度，所以訂閱這一步不花錢。
- **資格在 LINE 端檢查**：收到訂閱關鍵字時，後端依下一節的規則判斷。
  - 符合：訂閱成功，回覆已訂閱的項目。
  - 不符合：不建立訂閱，回覆缺哪一項（還沒綁定邀請碼，或入金還沒到 200 USDT），並接到現有的 UID 登記與核實流程（`src/automation.ts`、`src/bingx.ts`）。資格達成後，請用戶回到網站再按一次，或直接在 LINE 重送關鍵字。
  - **每次推播前再查一次資格**：核實後來被改成 `rejected` 的用戶就停止推播。
  - 網站按鈕旁邊要註明「需綁定 BingX 邀請碼並入金 200 USDT」，免得用戶跳到 LINE 才發現不能用。

- 後端沿用現有的關鍵字指令模式（`src/bot.ts` 的「訂閱報單 BTC」），以及報單的逐人投遞（`src/signals.ts`：佇列、租約、重試、額度檢查），但資料表要獨立，不和報單品項混用。新的 migration 編號是 **0016**。
- 開發前要實測：
  - 還沒加好友的用戶走這個流程時 LINE 怎麼處理。推播只送得到好友，確認訊息要引導加好友。
  - 電腦版瀏覽器點按鈕的體驗（通常會顯示 QR code）。

### LINE 通知的資格（2026-10-22 決定）

使用者原話：「邀請碼並且入金 200u」；接著決定「VIP 也改成要入 200u，內部轉帳不算」。

- **和 VIP 入群用同一套資格**：綁定邀請碼（`exchange_accounts.referral_status = 'verified'`，含團隊歸屬與 KYC）**並且入金 200 USDT，內部轉帳不算**。
- 這**改變了現有的 VIP 規則**。VIP 原本是「有入金就算，不設最低金額，允許內部轉帳」（2026-09-14，[BINGX-INTEGRATION.md](BINGX-INTEGRATION.md)），看的是 BingX 的 `deposit=true`，不看金額。新規則要改程式（`src/automation.ts`、`src/bingx.ts`）、網站與 LINE 文案，尚未實作。
- **金額從哪裡來**：BingX 的 `deposit=true` 不分內部轉帳，所以要改用 `deposit_records`（近 60 日入金明細，含金額與 `bizType`），排除內部轉帳後加總。要注意：
  - 只涵蓋近 60 日，不是帳戶的終身累計（[AUTOMATION.md](AUTOMATION.md)）。
  - 明細沒有「已完成」狀態欄位，也可能把完全相同的兩筆合併。
  - 因此用明細判斷「是否達到 200 USDT」可以，但不能當成對帳。
- **計算方式**（2026-10-22 決定）：核實當下往回 **60 日內累計入金達 200 USDT**（排除內部轉帳），正好是 `deposit_records` 涵蓋的範圍。
- 一旦達到門檻，就把「已達 200 USDT」記錄下來（時間與依據），之後不因為明細超過 60 日而失去資格。
- **已經入群的 VIP 直接可用**（2026-10-22 決定）：舊規則下已入群的用戶不必補到 200 USDT，可以直接開通 LINE 通知。
- **一份資格、兩項權益**（使用者原話：「所以能用訂單流軟體的也可以讓該用戶加入 VIP」）：
  - 符合資格的人同時可以加入 VIP 群、開通 LINE 訂單流通知。
  - 從警報訂閱流程來、核實通過的用戶，也照現有流程寄 VIP 邀請（`vip-delivery`）。
  - 已入群的 VIP 送出訂閱關鍵字，直接訂閱成功。
  - 對外文案可以合併成一句：「綁定邀請碼並入金 200 USDT，解鎖 VIP 群與 LINE 訂單流通知。」

### 關鍵字格式：方案 A（2026-10-22 決定）

| 方案 | 例子 | 優點 | 缺點 |
| --- | --- | --- | --- |
| A 可讀關鍵字 | `訂閱警報 吸收,掃蕩,冰山` | 透明、和現有指令一致、不用另外存資料 | 字串較長；用戶可以修改（但無害） |
| B 短代碼 | `訂閱 MB-7K2Q` | 字串短，可以記錄來源（哪支影片） | 用戶看不懂自己訂了什麼；要在伺服器存選項 |

使用者選 A。完整例子：`訂閱警報 吸收,掃蕩,冰山 每天3則 安靜00-08`（事件類型、每天則數、安靜時段）。若之後需要追蹤來源，可以在後面加簡短的來源標記，例如 `#yt01`。

### 訂閱管理：網站做 LINE Login（2026-10-22 決定）

只靠關鍵字的話，網站不知道用戶是誰，無法顯示「你目前訂閱了哪些」。使用者選擇在網站做 **LINE Login**，不做中間的簽章連結。

- 用戶用 LINE 登入網站後，可以直接看到並修改自己的訂閱（事件類型、每天則數、安靜時段）。
- 要另外申請 LINE Login channel，而且必須和官方帳號在同一個 provider 底下，才拿得到同一個 user ID，對得上 CRM 的客戶與資格。
- 登入後的 session 沿用後端現有的作法，不把 LINE user ID 放進網址或送到外部服務（VISION 原則 7）。
- LINE Login 上線之前，修改訂閱就重送一次關鍵字（新的設定覆蓋舊的），取消就在 LINE 傳「退訂警報」。
- 有了 LINE Login 以後，也是之後會員與付費功能的基礎（VISION 路線圖第 3、4 階段）。

## 網站介面比 LINE 好在哪裡

每一種警報一張卡片：

- 一句白話說明（在哪個關鍵位發生了什麼）。
- 一段小動畫，或真實案例的截圖，並連到實驗室。
- 對應的學院課程連結。
- 大概的發生頻率（例如「平均一天約 N 次」，用影子模式的實際紀錄計算）。**不寫命中率**。

## 成本

網頁通知不花錢。LINE 通知只開放給綁定邀請碼並入金 200 USDT 的用戶，而且只推關鍵位上的事件，量會比較少，但仍然是推播才花錢。

**決定先用免費方案**（每月 200 則，和行銷推播、報單、健康通知共用），真的不夠用再升級。估算：每人每天 3 則 × 30 天 = 90 則，所以免費額度大約只夠 2 位訂閱者收滿一個月。因此要做到：

- **額度不夠時直接放棄過時的事件**，不排隊等（[ORDERFLOW-KEYLEVEL-ALERTS.md](ORDERFLOW-KEYLEVEL-ALERTS.md) §7）；而且要保留額度給報單和行銷推播，不能被警報吃光。
- 管理頁要顯示本月已用量和警報佔多少，接近上限時通知管理員，作為「該升級了」的判斷依據。
- 可以搭配的做法：每人每天上限、安靜時段、每日摘要。

## 進度

開發順序：1. 統一圖表與警報的事件；2. 網頁通知；3. 訂閱頁與實驗室面板；4. LINE 關鍵字訂閱、逐人推播與 VIP 新規則；5. LINE Login。

**第 1 步（2026-10-22，分支 `feat/alert-unify-levels`，尚未部署）**：

- 關鍵位改成 UTC 日（`keylevels.js`）；2026-10-20 的回測腳本仍用台灣日，結果可以重現。
- 「在關鍵位」的門檻統一成 0.1%（`signals.js` 原本是 0.15%）。實驗室的前日關鍵位改用 `keylevels.js` 的算法。
- 收集器在每根 5 分 K 收盤後跑吸收、掃蕩收回、CVD 背離、不平衡區回測、放量突破（`closedBarEvents()`），和其他事件一樣經過關鍵位閘門。
- 每個市場事件都記下價位、方向，以及是否在關鍵位（`near`）。新增公開端點 `GET /api/orderflow/btcusdt/events`，只列在關鍵位的事件。
- 實驗室的「事件」在即時模式改成顯示這份紀錄；回放模式仍在網頁上偵測。
