# 關鍵位訂單流異常警報：MVP 實作計畫

狀態：規劃（2026-10-20），尚未開發。這份文件只盤點現有程式並提出做法，功能程式碼沒有修改。相關文件：[VISION.md](VISION.md)（第三支柱「警報與訊號訂閱」）、[ORDERFLOW-PLATFORM.md](ORDERFLOW-PLATFORM.md)（收集器與現有通知）、[ORDERFLOW-SIGNALS-PLAN.md](ORDERFLOW-SIGNALS-PLAN.md)（偵測器與過去的回測）。

## 產品定義

數據量比不過 Coinglass、Velo、TradingView，所以走差異化：**中文、教學，以及只在關鍵位推播的 LINE 精準警報**。

- **只在價格到了關鍵位才推播**。關鍵位包括前日高／低、VWAP、前日 Value Area 邊界（VAH／VAL）、前日 POC，以及還沒被回測過的失衡堆疊區。
- **推播的是當下的訂單流異常**：極端失衡、吸收、流動性掠奪後瞬間收回、大單突然撤單或瞬間堆疊、冰山單。零碎的 Delta 翻轉不推。
- **數量少、內容精準，手機一看就懂**：一句白話，加上一張圖卡或一個連結。
- 沿用 VISION 的原則：**事件不是指令**。描述「發生了什麼」，不寫進出場，訊息附「非投資建議」。

## 先講結論

1. **偵測器可以直接搬進收集器跑**。`signals.js` 和 `strategy-failed-auction.js` 都是不碰 DOM、不連網路、不讀時鐘的 ESM 純函式（只依賴 `metrics.js`）。收集器已經用同樣的方式 import `watch.js` 和 `bybit.js`。用兩天的 1 分鐘資料跑一次全部偵測器約 6 ms，每 5 分鐘跑一次，CPU 負擔可以忽略。
2. **位置過濾適合做成 `alert()` 前面的一道閘門**。新增一個共用模組 `keylevels.js`，負責維護當下的關鍵位清單；事件價格離最近的關鍵位不夠近，就記成 `offlevel`，只記錄不推送。現有的冷卻、每分鐘合併、每日上限都可以繼續沿用。
3. **擴充到訂閱者的主要成本是 LINE 額度**。後端已經有報單（`signals.ts`）那一套逐人投遞：佇列、租約、重試、配額檢查。照抄這個模式就好，新增 migration **0016**（`0015_delivery_recovery.sql` 已經存在；CLAUDE.md 寫「下一個是 0015」，那句已經過時）。試用版建議用「標籤限定名單、一對一推播」，先限 20 人以內、每人每天最多 3 則。
4. **回測（Bybit，2026-10-01 至 10-19，共 19 天）結果**：位置過濾能把量壓下來，但**沒有讓命中率變好**。「只碰到關鍵位」的基準命中率是 49%；吸收、掃蕩、背離在關鍵位的命中率是 41～53%，和基準一樣或更差。唯一看起來有希望的是「**極端 Delta 被吸收**」（1 分鐘 Delta 的 z ≥ 3，但收盤收回 K 棒另一半），在關鍵位命中 56～75%。不過只有 27 次，而且我們總共試了十幾種組合，這個數字可能只是運氣。這和過去用一年幣安資料得到的結論一致（[ORDERFLOW-SIGNALS-PLAN.md](ORDERFLOW-SIGNALS-PLAN.md)）。
5. 因此 MVP 定位成「**關鍵位注意力提醒＋教學**」，不要定位成「反轉訊號」。對外不宣稱命中率（VISION 原則 1）。90 天回測沒有任何事件類型通過（第 5b 節），所以 2026-10-20 決定：警報只是提醒，每則描述發生了什麼、接下來看什麼，並附即時實驗室和課程的連結，要不要進場由讀者看後續的訂單流判斷（第 8 節）。

## 2. 偵測器搬進收集器（問題 1）

### 純度與資料依賴

| 函式 | 是否純函式 | 輸入 | 收集器取得方式 |
| --- | --- | --- | --- |
| `aggregate(rows, tick, readings, now)` | 是（每次呼叫都建立新物件） | 1 分鐘列 `[t,o,h,l,c,levels]`、OI 讀數 `[t, oi, …]` | `bars` 表＋記憶體中的 `this.bars`；`oi`／`oi_rest` 表（收集器已經存成讀取時間，**不要**再經過 `fromArchive`） |
| `detect(bars, kinds)` | 是。冷卻狀態放在函式內部；`stacked` 會把結果暫存在 bar 物件的 `b.stack` 上，但 bar 物件每次都重新建立 | `aggregate` 的輸出 | 同上 |
| `valueArea()`、`dayProfiles()` | 是 | 一天的價位成交量 | 前一個 UTC 日的 `bars` 表 |
| `findFailedAuctions()` | 會**暫時改寫模組層級的 `P`**，結束時在 `finally` 改回來。DO 是單執行緒、同步執行，所以安全 | 1 分鐘列、讀數 | 不搬，理由見上 |

注意事項：

- `aggregate()` 的前日關鍵位是從**輸入資料本身**算出來的，所以輸入必須包含完整的前一個 UTC 日。前一天的封存檔約在 01:10 UTC 匯入，匯入後要用 `src='archive'` 的列重算一次前日關鍵位。匯入前那一小時，先用即時資料（`live`／`kline`）算出的版本，並在狀態裡註明。
- 關鍵位以 **UTC 日**計算，和網頁一致。台灣的「前一天」是 08:00 換日，這點要在訊息和課程裡講清楚，或者改成台灣日；這需要使用者決定，見最後一節第 6 項。
- 偵測器只看**已收盤**的 K 棒（`now` 參數），所以即時結果和回測一致。
- 兩份檔案裡的 `valueArea` 重複實作（`signals.js`、`strategy-failed-auction.js`），抽到 `keylevels.js` 合併成一份。

### CPU 成本（Node 22，與 workerd 同為 V8）

| 工作 | 每次耗時 |
| --- | --- |
| 2 天的 1 分鐘列 → 5 分 K（`aggregate`） | 2.8 ms |
| 576 根 5 分 K 跑預設偵測器（`detect`） | 5.7 ms |
| 只跑最近 300 分鐘、三種偵測器 | 0.3 ms |
| 一天的 `dayProfiles` | 0.8 ms |
| `findFailedAuctions`（2 天／19 天） | 3.2 ms／27 ms |

每 5 分鐘一次，加上從 SQLite 讀 2,880 列再 `JSON.parse`（約 400 KB），總共估計不到 20 ms，遠低於每次呼叫 30 秒 CPU 的上限。也可以把最近 2 天的 5 分 K 留在記憶體裡、逐根追加，但第一版用「每次重算」比較簡單，也最不容易和回測不一致。

## 3. 位置過濾層（問題 2）

### 關鍵位從哪裡來

新增 `public/lab/orderflow/keylevels.js`（純函式，網頁、回測、收集器共用）：

| 關鍵位 | 計算方式 | 更新時機 |
| --- | --- | --- |
| 前日高、前日低、前日 POC、VAH、VAL | `dayProfiles()`（足跡 $10 價位，70% 價值區） | UTC 換日時算一次，前一天的封存檔匯入後重算 |
| VWAP | 當天累計 Σ(價位中點 × 量) ÷ Σ量，和網頁的算法相同 | 每分鐘收盤時更新（從 `persistBars` 的分鐘列累加）。換日後的第一個小時不算，因為那時 VWAP 幾乎就是現價 |
| 失衡堆疊區 | `stacked` 偵測器在 5 分 K 收盤時找出來的價區 | 2 小時內有效，第一次被回測後就移除（同 `stackedRetest`） |

收集器在記憶體中保留一個 `LevelBook`：`{ name, price, since }[]`，`/status` 和管理頁都顯示目前的關鍵位。

### 閘門

```
事件（watch.js 或 K 棒偵測器）
  → levelGate(e, levels, cfg)：從事件取出價格，找最近的關鍵位
      距離 ≤ 容忍距離 → e.level = { name, price, dist }，狀態 pending
      太遠            → 狀態 offlevel（記錄，不推送）
  → 冷卻：每個「關鍵位 × 方向」60 分鐘內只推一次（新增，和原本「每種事件 10 分鐘」的冷卻並存）
  → flushAlerts（每分鐘合併、每日上限）
```

每種事件拿來判斷位置的價格：

| 事件 | 判斷位置用的價格 | 預期方向（給命中率統計用） |
| --- | --- | --- |
| `print` 大單 | `price` | 依接近方向判斷反轉 |
| `liq` 連環爆倉 | 多單被強平用 `low`，空單被強平用 `high` | 多單被強平 → 往上；空單被強平 → 往下 |
| `oi` | 最新成交價 | 無（只當作附註，不單獨推送） |
| `wall`／`wall_eaten`／`wall_pulled`／`spoof` | 價位帶 `price`（取價位帶中點） | 牆被撤或疑似誘單 → 往牆的反方向 |
| `iceberg` | `price` | 買方冰山 → 往上；賣方冰山 → 往下 |
| K 棒偵測器（吸收、掃蕩收回、堆疊回測、極端 Delta 被吸收） | 偵測器回傳的 `price` | 偵測器回傳的 `dir` |

容忍距離的單位：Bybit 的最小跳動是 $0.1，用 tick 來表示距離沒有意義；足跡的價位格距是 $10。建議用**百分比**：`levelTolPct`，預設 0.10%，約 $80。再加一個最小值 `levelTolUsd`（預設 $20），避免價格很低時容忍距離太窄。回測中 0.05% 和 0.15% 的差別見第 5 節。

新增的設定，放進 `ALERT_DEFAULTS`，沿用 `validSetting()` 和管理頁：

| 設定 | 預設 | 說明 |
| --- | --- | --- |
| `levelOn` | 1 | 0 = 不過濾（回到現在的行為） |
| `levelTolPct` | 0.1 | 百分比 |
| `levelCooldownMs` | 3,600,000 | 每個關鍵位、每個方向 |
| `levelVwap`、`levelPoc`、`levelStack` | 1 | 個別關掉某一類關鍵位（POC 和堆疊區在回測中最雜） |
| `dailyCapTrial` | 3 | 給試用者的每日上限；管理員維持 30 則 |

健康通知（`HEALTH_KINDS`）和 `test` 不經過閘門。

### 訊息格式（手機）

每則 = 一句白話描述發生了什麼 + 一句「接下來看什麼」 + 一張 Flex 卡片 + 兩個連結：當下那一分鐘的即時實驗室（`/lab/orderflow/?tf=1&at=<分鐘>`）與對應課程。**不寫方向**：不寫「可能反轉」「看空」「進場」，只描述發生了什麼，並請讀者看後續的訂單流再判斷（第 8 節，2026-10-20 決定）。

```
🐻 BTC 到了前日高 82,450
買方 1 分鐘內砸進 +420 BTC，價格沒有跟著上去
接下來看：後面幾分鐘買方還有沒有力氣、價格站不站得穩 82,450
→ 打開即時足跡圖（就在這一分鐘）
→ 課程：吸收是什麼
盤面提醒，不是買賣建議
```

- **圖**：在 Worker 裡把圖表畫成 PNG，要用 Browser Rendering 或 resvg-wasm，成本和複雜度都太高。第一版改用 LINE **Flex Message** 畫一張「關鍵位梯子」：列出幾個價位、目前價格的位置，以及事件標記。不需要另外託管圖片，在手機上一眼就能看懂。之後如果真的需要截圖，再評估 Browser Rendering。
- 每種事件附對應課程的連結，`SIGNALS[kind].lesson` 已經有對照，這就是「教學」的差異化。
- `describe()` 新增「白話版」的寫法，例如 `describeShort(e)`，並在句子裡帶出關鍵位的名稱，加上一句依事件類型固定的「接下來看什麼」（例如吸收：「看這一側還有沒有人繼續追」；掃蕩收回：「看價格能不能留在關鍵位內側」）。原本給管理員看的技術版保留。

### 缺少的偵測器

| 使用者列的事件 | 現況 | 做法 |
| --- | --- | --- |

## 4. 從管理員擴充到訂閱者（問題 3）

### LINE 額度與成本

LINE 官方帳號台灣方案（2023-09 起；第三方整理指出 2026-11-01 起月費可能調整，**以官方公告為準**）：

| 方案 | 月費（未稅） | 每月免費則數 | 加購 |
| --- | --- | --- | --- |
| 輕用量 | 0 | 200 | 不可 |
| 中用量 | NT$800 | 3,000 | 不可 |
| 高用量 | NT$1,200 | 6,000 | 約 NT$0.2／則起，量越大越便宜 |

- 推播（push）**一個收件人算一則**；一次推播最多 5 個對話框，仍然只算 1 則。回覆（reply）不計費。
- **推到群組是否依群組人數計算**，要向 LINE 官方確認。依 Messaging API 的說明，推到群組時應該是以成員數計算，不會比一對一便宜。
- 試算：每人每天上限 3 則，30 天就是每人 90 則。中用量 3,000 則大約只夠 **30 人**，而且還要和行銷推播、報單共用額度。100 人、每天 3 則，一個月是 9,000 則，高用量月費 1,200 元，加上超出的 3,000 則 × 0.2 元，合計約 NT$1,800／月。
- 省額度的做法：每日上限、只推達標的事件類型；用「**回覆**」提供查詢，例如使用者輸入「關鍵位」就回傳目前的關鍵位和最近的事件，回覆不計費；網站上的事件列表免費。

### 三種最小版本比較

| | A. 標籤限定名單、一對一推播（**建議**） | B. LINE 群組 | C. 只推管理員，再由人工轉發 |
| --- | --- | --- | --- |
| 額度 | 人數 × 則數，可以預估 | 依成員數計算（待確認），一樣不便宜 | 只算 1 人 |
| 個人退訂 | 有（LINE 指令） | 只能退群 | — |
| 隱私 | 好，彼此看不到 | 成員互相看得到 | — |
| 開發量 | 中：照抄報單的投遞流程 | 中：bot 目前**沒有**處理 `join` 事件，也沒有存 `groupId` | 零 |
| 驗證價值 | 能量測每個人的退訂率和點擊率 | 能看討論，但比較吵 | 低 |

### 後端要做的事（方案 A）

1. **Migration `0016_orderflow_alerts.sql`**
   - `orderflow_alert_subs(line_user_id PK REFERENCES customers, source TEXT CHECK(source IN ('trial','admin')), created_at, created_by, expires_at)`。試用名單由管理員在 `/admin` 加入，不開放自助加入；LINE 指令只能**退訂**。
   - `orderflow_alert_messages(id PK, alert_key UNIQUE, text, flex_json, kinds, created_at, audience_count, status CHECK IN ('queued','completed','halted'))`。
   - `orderflow_alert_deliveries(id PK, message_id, line_user_id, status, attempts, first_attempt_at, lease_until, finished_at, detail, UNIQUE(message_id, line_user_id))`，欄位和 `signal_deliveries` 相同。
   - `ALTER TABLE team_settings ADD COLUMN orderflow_alerts_enabled INTEGER NOT NULL DEFAULT 0`：預設關閉的急停開關。
2. **`src/orderflow-alert.ts`**：body 加上 `audience`。`trial` 時在同一個 D1 batch 裡建立訊息和逐人投遞列，`alert_key` 用來防止重送。之後呼叫 `dispatchOrderflowAlerts()`，5 分鐘的 cron 也會呼叫一次，接手中斷的投遞。
3. **投遞**：照抄 `deliverSignal`。每一筆都要重新檢查 `LINE_DELIVERY_MODE === "live"`、急停開關、是否仍在名單且沒有封鎖。使用 `X-Line-Retry-Key`；**超過 15 分鐘還沒送出的警報直接標為 `skipped`**，因為過時的盤面事件沒有價值，這點和報單的 23 小時不同。
4. **額度**：建立訊息前用 `lineQuota()` 減掉 `reservedLineMessages()`，不夠就不建立，並回報給收集器。`reservedLineMessages()` 也要把警報的待投遞數算進去。
5. **LINE 指令**（`bot.ts`）：「關鍵位警報」顯示目前狀態，「退訂關鍵位」退出名單，「關鍵位」用回覆查詢目前的關鍵位（不計費）。
6. **收集器**：`flushAlerts()` 照舊送給管理員（技術版文字）。只有同時符合三個條件的事件，才另外送一份 `audience:"trial"`：通過位置閘門、事件類型在 `trialKinds` 白名單內、當日未達 `dailyCapTrial`。LINE 使用者 ID 只存在後端，收集器拿不到。
7. **防護**：三層防護缺一不可。收集器 `ORDERFLOW_ALERTS=live`、後端 `LINE_DELIVERY_MODE=live`，再加上 `orderflow_alerts_enabled=1`。本機和測試環境三者預設都是關閉的。

### 測試

- `tests/*.test.mjs`：`keylevels.js`（VWAP、前日關鍵位、堆疊區的有效期限）、`levelGate`（容忍距離、冷卻）、`FlashWallWatch`；做法和 `watch.js` 現有的測試一樣，用自己編的串流驅動。
- `tests/*.test.ts`（Miniflare）：`/api/internal/orderflow-alert` 的 `audience:"trial"` 會建立投遞列；delivery 沒有設為 `live` 或急停開啟時，不會呼叫 LINE（stub `fetch` 記錄呼叫次數）；退訂後會跳過；過期的投遞會被標為 skipped；額度不足時拒絕建立。

## 5. 回測（問題 4）

### 資料與方法

- 資料：Bybit BTCUSDT，**2026-10-01 至 10-19，共 19 天**，取自正式 API `/api/orderflow/btcusdt/day`（與網頁讀的是同一份資料；這段期間的足跡都由封存檔重建，和 `npm run lab:orderflow:bybit` 產生的相同）。爆倉只有 10-15 之後的 5 天。

- 腳本：暫時放在共用筆記資料夾（`keylevel-backtest.mjs`、`result.txt`），第 0 階段會正式整理成 `scripts/orderflow-keylevel-backtest.mjs`。

## 5a. 第 0 階段：事先登記（2026-10-20，在看 90 天結果之前寫下並 commit）

以下定義與通過標準在下載和執行 90 天回測**之前**就固定。看到結果後不再修改；之後要改參數，就是一次新的登記，而且必須用還沒看過的資料（例如 10 月下旬之後的前瞻資料）。

### 資料與切分

- Bybit BTCUSDT 每日成交封存檔，UTC 2026-07-01 至 09-30（92 個檔案），用 `bybit.js` 的 `ArchiveDay` 重建成 1 分鐘足跡；大單用封存檔估計值（同一毫秒、同一方向合併）。
- OI：Bybit REST 5 分鐘 `open-interest` 歷史，時間戳就是讀取時間。
- 評估期間是**台灣日** 2026-07-03 至 09-30，共 90 天。台灣 07-02 只拿來當第一天的「前一日」。
- **調參段**：台灣 07-03 至 08-16（45 天）。**驗證段**：台灣 08-17 至 09-30（45 天）。通過與否**只看驗證段**；調參段只用來檢查方向是否一致。
- 不使用 10-01 至 10-19：第 5 節已經看過這段資料，它是產生假設的發現段。
- 不測：連環爆倉（沒有 90 天的爆倉歷史）；掛單牆、誘單、冰山（沒有歷史掛單簿）。這幾種只在影子模式中前瞻記錄。

### 固定定義

- **關鍵位**（台灣日，以 Asia/Taipei 午夜，也就是 16:00 UTC 換日）：前一個台灣日的高（PDH）、低（PDL）、POC、VAH、VAL（$10 價位、70% 價值區）；當天 VWAP（從台灣 00:00 起累計，開盤後第一個小時不算）；堆疊區（已收盤 5 分 K 的 `stacked` 偵測器所找到的價區中點，2 小時內有效，第一次被碰到之後再保留 5 分鐘）。
- **位置**：事件價格距離最近的關鍵位 ≤ 事件價格的 0.10%。
- **冷卻**：同一種事件 × 同一個關鍵位 × 同一個預期方向，60 分鐘內只算一次。
- **事件**（參數用 `signals.js` 的 `P` 和 `watch.js` 的 `ALERT_DEFAULTS` 目前的值）：
  - `deltaSpikeAbsorbed`（**主要假設**）：1 分 K 的 Delta 以前 240 分鐘為基準，z ≥ 3（或 ≤ −3），收盤落在 K 棒另一半（買方爆量收在下半部，預期往下；賣方爆量收在上半部，預期往上）。同一種極端 Delta 事件之間至少間隔 10 分鐘。
  - 探索性：`deltaSpike`（同上，但沒有被吸收；不帶方向）、`absorption`、`sweep`、`stackedRetest`、`divergence`（5 分 K，方向由偵測器決定）、`print`（單筆主動單 ≥ 50 BTC）、`oi`（`OiWatch`）。
  - 沒有方向的事件，預期方向設為「反轉接近方向」：事件發生前 30 分鐘的收盤價低於事件價格，就預期往下；反之預期往上。
- **進場價**：從事件時間所在的那一分鐘（事件剛好落在整分鐘時，就是從那一刻開始的那一分鐘）的收盤價；從下一分鐘開始計算結果。
- **命中**：進場後 60 分鐘內，價格先往預期方向走 0.2%，才往反方向走 0.2%。同一分鐘兩邊都碰到算失敗；兩邊都沒碰到算「未決」，不計入命中率，但另外報告未決的比例。0.4% 只當參考，不用來判斷是否通過。
- **基準**：只碰到關鍵位。每根 1 分 K 的價格範圍進入關鍵位 0.10% 以內就算一次，冷卻規則相同，預期方向依接近方向判斷；進場價取該分鐘的收盤。
- 標準誤 SE = √(p(1−p)/已決定次數)。

### 通過標準（只看驗證段）

| | 主要假設 `deltaSpikeAbsorbed` | 探索性事件（7 種） |
| --- | --- | --- |
| 已決定次數 | ≥ 30 | ≥ 30 |
| 命中率 − 基準命中率 | ≥ 2 SE | ≥ 3 SE（7 個比較，提高門檻） |
| 調參段 | 命中率也高於基準 | 同左 |
| 頻率 | 驗證段平均每天 ≤ 3 次 | 同左 |

通過的事件類型，在第 2 階段才可以列入推播白名單；沒有通過的維持只記錄。

  - 每個市場事件都會記下最近的關鍵位與距離：`alerts` 表新增 `level`、`dist` 兩欄，訊息文字後面加上「｜前日高 82,450（差 $35）」。
  - 新設定：`levelOn`、`levelTolPct`、`levelCooldownMs`、`dailyCap`（預設 3，取代原本固定的 30）。
  - 新狀態：`offlevel`（不在關鍵位）、`repeat`（同一關鍵位冷卻中）。
  - `/status` 和管理頁會列出目前的關鍵位，管理頁多了「只推關鍵位附近」的開關和三個門檻。
  - K 棒偵測器和白話訊息屬於第 2 階段，沒有做。部署（`npm run orderflow:deploy`）要另外決定。

每一階段都在功能分支上開發，合併到 `main` 只會發布網站；Worker 要手動部署（`npm run orderflow:deploy`、`npm run deploy`），migration 也要手動執行，所以要在發布那一步明確決定。

## 7. 風險

- **把「到關鍵位」誤當成「會反轉」**：回測顯示關鍵位常常被突破。訊息只描述發生了什麼，不寫「可能反轉」，並連結到教「守住或翻轉」的策略 02 課程。
- **過度擬合**：只有 19 天資料，又試了很多種組合。第 0 階段一定要事先登記通過標準，並用驗證段確認。
- **LINE 額度**：和行銷推播、報單共用。額度不夠時，事件應該直接放棄，不要排隊等（過時的事件沒有價值）。
- **延遲**：5 分 K 偵測器要等收盤，最多晚 5 分鐘；收集器每 10 秒一次 alarm，加上每分鐘合併，最多再晚 1 分鐘。「瞬間」類的事件（誘單、冰山、極端 Delta）要直接走即時路徑。
- **收集器重啟**：掛單簿類的觀察器重啟後狀態會清空（例如持續 60 秒的條件要重新累積），可能漏報；不能補報舊的事件。
- **前日關鍵位的資料品質**：封存檔匯入前用的是即時資料，中間如果有缺口，前日高低可能偏差。匯入後重算，偏差超過 $10 時記錄到 `/status`。
- **法規與形象**：推播頻率與用語不能像喊單；所有訊息都附「非投資建議」；不對外公布命中率（VISION 原則 1、4、5）。
- **資料授權**：把 Bybit 資料商用推播給會員之前，要先確認交易所的條款（VISION 原則 6）。
